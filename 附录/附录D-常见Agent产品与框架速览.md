## D.1 Coding Agent 产品（品类最成熟，参见第 23 章）

**Claude Code（Anthropic）**：终端形态 Coding Agent 的代表，也是本书多处机制的现实原型——TODO 驱动规划（第 4 章）、CLAUDE.md / Skills / Hooks 三控制面（第 6 章）、str_replace 编辑与修复环（第 23 章）、子代理与 MCP 接入（第 8 章）。集成形态覆盖第 12 章的方式一（CLI/PTY）与方式二（Claude Agent SDK——Harness 库化的实例）。用它做"生产级 Harness 长什么样"的参照读物，比读任何框架文档都直观。

**GitHub Copilot（agent 形态）**：IDE 原生分发 + 与 PR/评审流程深度整合的路线。定位启示：**分发渠道本身是 Harness 之外的第七件**——同等机制质量下，住在工程师已有工作流里的产品采用阻力最小（第 22 章组织视角的印证）。

**Cursor**：IDE 整体形态（编辑器即产品），自建代码索引与检索栈——第 11 章"语义检索路线"在 Coding 场景的代表实现，与 grep 路线（第 11 章 2.6 节）构成现实中的两条技术路线对照。

**Devin（Cognition）类"自主软件工程师"**：云端工作区 + 浏览器 + 长时程任务的全自主叙事代表。工程教训恰是第 1 章的自主性光谱：演示的全自主与生产的 HITL 需求之间的落差，是这一类产品口碑波动的共同根源——评估时按第 13 章"自主性按风险配置"检验其审批与回滚设施，而非看演示视频。

**云端异步 Coding Agent（Codex 类 / 各家后台任务形态）**：任务进队列、云沙箱并行执行、以 PR 为交付物——第 23 章"并行 worktree 开发"的托管版：隔离（第 13 章）、门禁（第 18 章 GUARD/CI）、人守 merge 闸口，三件套一样不少，只是搬进了云。

## D.2 通用助手与计算机操作（成熟度：早期采用）

**Computer Use / Operator 类**（各家的浏览器与桌面操作 Agent）：以屏幕截图 + 点击键入为行动空间——OSWorld/WebArena（第 15 章）测的正是这类能力。现状判断用第 24 章三问：生产信号仍集中在表单填写、网页流程等窄场景；宽场景的成功率与延迟尚不支撑 SLA。它的结构性难点本书都讲过：验证信号稀薄（点完按钮"成没成"难判——对比第 23 章编译测试的富信号）、副作用难分级（页面上一个按钮可能是任何等级的操作，第 9 章分级失去静态判据）。

**Manus 类通用任务 Agent**：云端沙箱 + 浏览器 + 文件工作区的组合——第 9 章"文件系统即工作区"结论在非 Coding 场景的产品化印证；其"规划-执行分离 + 交付物落盘"的形态即第 4 章 P2E 与工作区模式的合体。

## D.3 深度研究类（Deep Research 形态）

各家 **Deep Research** 产品（多轮检索 → 交叉验证 → 长报告）：第 11 章 Agentic RAG（检索即工具、追加检索回路）+ 第 4 章显式规划 + 引用溯源的产品化集成，是"非 Coding 领域找到富验证信号"的一次成功示范——它的验证信号是**引用可回查**（每个结论锚到来源），部分替代了代码领域的测试。长时程（数分钟到数十分钟）运行依赖的正是第 12 章的生命周期管理与第 3 章的预算设施。

## D.4 低代码 / 工作流平台

**Dify、Coze（扣子）、n8n 及同类**：可视化编排 LLM 节点 + 工具节点的平台。用第 1 章 2.5 节的语言精确定位：**它们主要是 Workflow 产品，不是 Agent 产品**——控制流由画布上的连线（人）决定，模型在节点内填空。这不是贬义：路径可枚举的场景（客服 FAQ、审批流、内容管线）本就该用 Workflow（第 1 章的选型法则），这类平台是该形态的最低成本落地。边界也随之清晰：开放探索任务上它们的"Agent 节点"能力有限，且第三篇的生产件（评测/观测/成本归因）在平台内的深度参差——按第 12 章六大件逐件检查再定深度绑定。

## D.5 编排框架（代码库）

**LangGraph（LangChain 谱系）**：第 18 章显式图执行的最流行开源实现——state / conditional edges / checkpointer / interrupt 与本书图执行器的概念一一对应（读完第 18 章再看它的文档，会发现只剩 API 记忆工作）。LangChain 本体则是工具与集成的生态层，第 2 章的心智模型提醒依然适用：框架封装的是那 40 行循环，会手写才谈得上选型。

**CrewAI**：角色化多 Agent 的模板化封装（Supervisor / Pipeline 风格开箱即用）。用第 17 章语言评估它给的模板各是什么拓扑、代价系数多少；第 1 章坑 5（过早多 Agent）在这类"五分钟起多 Agent"的框架用户里发生率最高——Checklist（第 17 章）先行。

**AutoGen（Microsoft）**：对话式多 Agent（GroupChat 谱系）与事件驱动运行时。其"Agent 间自由对话"形态对应第 17 章 Debate/Swarm 的混合——token 放大与可预测性的账（第 17 章表）要先算。

**OpenAI Agents SDK / Swarm 谱系**：handoff 原语的命名来源（第 17 章 Swarm 拓扑）；轻量、贴近裸循环，适合验证概念。

**Claude Agent SDK**：Claude Code 的 Harness 以库形式开放——第 12 章"方式二：SDK 嵌入"的直接实例，也是"买六大件、自建定制层"路线的代表。

**框架选型的通用姿势**（本书立场重申）：先用第 2 章的手写循环建立心智模型 → 用第 12 章六大件清单逐件检查候选框架的实现与可替换性 → 缺的件按第三篇对应章节自建。**框架是六大件的采购清单，不是架构的替代品。**

## D.6 托管运行时与云服务

**云厂商 Managed Agents / Bedrock Agents / Vertex AI Agent Builder 及同类**：Harness 六大件的云服务化（第 24 章"运行时标准化"档位：早期采用）。与第 20 章部署光谱交叉评估：它们通常落在第二档（VPC/云边界内），买到的是运维与合规资质，让出的是 Harness 定制深度——"自建 K8s → 托管 K8s"的历史在 Agent 运行时上重演，迁移判断也同构：标准件托管、差异件自持。

## D.7 开源 Coding Agent 与社区生态

> **核验强度警告**：本节多为社区/新兴项目，迭代与更名极快，个别条目的**具体形态本书未能完全确证**，已逐条标注核验状态。发行前必须按附录 C 的 [C-06] 逐项核实其真实定位、归属与存续，无法确证者删除而非保留——**宁可少列一个，不可错述一个**。

**opencode**（SST 社区，开源）：终端形态的**模型无关（provider-agnostic）Coding Agent**——同一套 Harness 可后端接 Claude、OpenAI 或本地模型，卖点正是"不锁定单一供应商"（第 20 章退出成本的一种规避）。定位坐标：自带六大件的完整 CLI/TUI 产品，集成方式对应第 12 章"方式一/自身运行时"，开源可自托管。与 Claude Code 的区别是**模型层可插拔**；代价是六大件的打磨深度通常滞后于厂商第一方产品（第 12 章 45%/78% 实验的含义——同模型下 Harness 成熟度仍是变量）。*核验状态：项目真实、活跃；细节以其仓库为准。*

**OhMyOpencode（OMO）**：从命名（对标 oh-my-zsh）判断，是 **opencode 的社区增强分发层**——一键装配提示词、Skill、Hook、以及**预置的多角色 Agent 团队配置**（D.10 选型表把它列为 OpenCode 上"最强多 Agent 虚拟团队"的首选，正是指这套预置团队；它本身不是独立 Agent，而是把多 Agent 编排打包进 opencode 的第 6 章三控制面）。*核验状态：待确认——按名称定位，其确切形态与维护状态发行前务必核实或删除。*

**Superpowers**：Claude Code 之上的 **Skill 集合 / 插件生态**（第 6 章 Skill 机制的社区放大），把一批可复用的任务技能打包分发，甚至含"用于安装技能的技能"。定位坐标：它不改 Claude Code 的循环，只扩充其程序记忆（第 10 章 Skill=程序记忆的落地）。价值与风险并存：Skill 正文会进上下文并被执行，第三方 Skill 是供应链面（第 8 章 2.4、第 13 章）——来源白名单 + 入库评审不可省。*核验状态：项目存在；具体技能清单与维护方以其仓库为准。*

**codex**（OpenAI）：OpenAI 的 Coding Agent 线，两种形态——**Codex CLI**（开源、终端、对标 Claude Code）与**云端异步 Codex**（任务进队列、云沙箱并行、以 PR 交付，即第 23 章"并行 worktree 开发"的托管版）。定位坐标：完整六大件，绑定 OpenAI 模型生态；选型时按第 20 章数据出域与条款、第 15 章自家评测集与 Claude Code 对标，而非看演示。

**openclaw**：*核验状态：待确认*——本书未能确证该名称对应的具体项目。若确为开源的 Claude Code 类编码/计算机操作 Agent，则按其形态归入本节或 D.2；发行前务必核实其真实存在与定位，**否则删除此条**（附录 C 纪律：无来源的产品名不进发布稿）。

**Claude Code**：Coding Agent 品类的第一方代表，完整介绍见 D.1，此处不重复；上述开源项目多以它为对标基准。

## D.8 模型侧 / 提供方 Harness

这一类的主体不是"应用产品"而是**模型 + 其配套 agentic 脚手架**——你自建 Agent 时把它作为第 20 章第三档（私有化开源模型）的候选来评估，坐标不在"集成方式"而在"能力/成本/合规"三角与 Agentic 任务实测。

**DeepSeek Harness**：DeepSeek 的开源权重模型（强推理线如 R1 系）+ 其配套的 agentic / 代码脚手架与评测框架。定位坐标：模型侧候选，卖点是**开源权重 + 强推理 + 成本优势**，适合第 20 章第三档（合规硬约束或大规模稳定负载）；评估必须用 **Agentic 任务集**而非问答集（第 20 章：开源与旗舰闭源的差距在工具调用可靠性/长程稳定性上最大）。*核验状态：DeepSeek 模型真实且开源；"Harness" 指其配套脚手架，具体名称与形态发行前核实。*

**Hermes Agent**：Nous Research 的 Hermes 开源模型家族以**函数调用 / 工具使用**的 agentic 微调著称（附录 A.4 训练谱系里 SFT/agentic 微调的社区代表）。定位坐标：同样是模型侧候选——当你要在私有化开源模型上自建工具调用型 Agent 时，它是评测候选之一；"Agent" 更多指其 agentic 微调取向而非一个成品应用。*核验状态：Hermes 模型家族真实；"Hermes Agent" 作为独立产品的形态待确认。*

## D.9 Vibe Coding（一种实践，不是产品）

**Vibe Coding** 是 Karpathy 于 2025 年提出的**工作方式术语**，不是任何具体工具：指"用自然语言把想法说给 Coding Agent、基本不细看生成代码、跟着感觉走（give in to the vibes）"的编码方式。之所以列入本附录，是因为它常被误当成一种"产品能力"来讨论，而它其实是**使用姿态**，且直接撞上全书的核心纪律：

- **适用区间**：一次性原型、玩具项目、探索性草稿——错误代价低、产物不进生产，vibe coding 效率极高，是 Agent 带来的真实生产力。
- **危险区间**：进生产的代码。全书反复论证的失败面在此集中兑现——不看 diff = 第 22 章 38 秒 LGTM 的极端版；无验收标准 = 第 15 章玄学调参；把测试变绿当修好 = 第 23 章坑 1。**vibe coding 到生产之间，隔着的正是本书第三篇（评测/观测/安全）与第 22 章（评审/Spec）的全部纪律。**
- **一句话定位**：vibe coding 是 Coding Agent 的"演示档位"，不是"生产档位"——从前者到后者的距离，就是这本书。

*核验状态：术语真实（Karpathy 2025 提出），此处按其公认含义描述。*

## D.10 同赛道开源项目分类速览（社区快照）

> **性质与核验**：本节是"给 AI 编码 CLI 增加工作流约束、子 Agent、多角色团队、任务拆解、TDD、规划评审"这一赛道的**社区项目快照**，条目多、更名与存续变动极快，本书**未逐一独立核验**，统一挂 [C-07]——发行前按项目仓库逐项复核，失效即删。用法不是"选一个抄"，而是用本书坐标（六大件 × 第 17 章拓扑 × 第 6 章 Skill/第 22 章 SDD）快速判断每个项目"到底给了什么、属于哪一格"。四大类：① OpenCode 插件；② Claude Code 生态插件；③ 独立完整 Agent；④ 工作流/技能套件。

**① OpenCode 插件**（与 OhMyOpencode 同底座，经 `opencode.json` 安装；与 Claude Code 插件**底座不同、不可混用**）：

- **CrewBee**：OpenCode 原生多 Agent 团队，自定义产品/后端/测试角色、可控并行——第 17 章 Supervisor/Parallel 的插件化；比 OMO 轻、token 开销低。
- **Slim（Pocket-Universe）**：轻量子 Agent，只做局部子任务拆解、不大规模并行，复用 OpenCode 钩子，适合中小项目。
- **Micode**：规划驱动（头脑风暴→方案→实现），擅长产出 spec 需求文档，子 Agent 能力中等。
- **Spec-Superflow**：Superpowers 衍生，**Spec-first 契约驱动**（第 22 章 SDD + OpenSpec 规划引擎），跨 OpenCode/Claude Code/Cursor/Copilot-CLI。
- **oh-my-superagents**：桥接 Superpowers 工作流，把 phase 计划自动生成 OpenCode 的 agents/commands 配置，减少手写。
- 社区总清单：`awesome-opencode`。

**② Claude Code 生态插件**（跑在官方 Claude Code CLI 上，不能跑在 OpenCode）：

- **oh-my-claudecode（OMC）**：热门多 Agent 编排层，约 21 个专业角色，`/team` 启动 plan→prd→exec→verify→fix 五阶段流水线（第 17 章 Pipeline + 角色团队），tmux 多进程隔离子 Agent。
- **Everything-claude-code**：13 个专家子 Agent + 40+ Skills + 会话记忆持久化 + 自动规范检查，一套配置升级 Claude Code。
- **Ruflo（claude-flow）**：Queen-Worker 蜂群模式（第 17 章 Hierarchical/Swarm 谱系），多进程分发/并行/合并，SPARC 工作流。
- **SuperClaude**：9 套预置专家 Persona + 大量斜杠命令/钩子，给官方 CLI 加虚拟团队。
- **Get-Shit-Done（gstd）**：极简套件，**不强制 TDD**、优先快速交付，与 Superpowers 的重型流程相反。
- **Coding-Workflow**：可组合 skills+agents、Hive 团队调度、多模型后端，TDD/安全审计/文档同步，模块化不写死流程。

**③ 独立完整 Agent**（不依赖 OpenCode/Claude Code，可直接运行）：

- **OhMyCode**（中科大 AlphaLab）：约 3k 行核心，轻量子 Agent 调度、可改自身源码，适合学习与二次开发。
- **Claw-Code**：Claude Code 的净室开源实现，完整钩子/子 Agent/MCP，可脱离 Anthropic 官方 CLI 复刻 OMO 式工作流。（对应 D.7 "openclaw" 一名的可能所指之一，仍需核验。）
- **OpenHands**（原 OpenDevin）：成熟的自主编码 Agent，多角色分工 + 沙箱执行，适合完整项目，资源消耗偏大。
- **MetaGPT**：经典软件多 Agent 团队（产品/架构/开发/测试）——第 17 章 Pipeline 的代表，**擅长从零生成新项目**，存量重构偏弱。
- **Goose**（Block，Apache-2.0）：Leader-Worker 简单多 Agent（第 17 章 Supervisor），MCP 原生、模型无关、插件友好。

**④ 工作流 / 技能套件**（跨平台，OpenCode/Claude Code/Cursor 通用）：

- **Superpowers**：见 D.7；强制 TDD + 头脑风暴 + git worktree 隔离 + 代码评审，**工程纪律优先**，子 Agent 少、不搞大规模并行。
- **Hyperpowers**：Superpowers 超集，加长期记忆、史诗级任务拆分、高级规划，更重。
- **OpenSpec**：**spec 契约驱动**（第 22 章 SDD 的独立工具化），先写规格再编码，可与 Superpowers 叠加。

**快速选型参考**（用途 → 首选；具体能力以项目当前文档为准）：

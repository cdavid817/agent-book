## D.1 Coding Agent 产品（品类最成熟，参见第 23 章）

**Claude Code（Anthropic）**：终端形态 Coding Agent 的代表，也是本书多处机制的现实原型——TODO 驱动规划（第 4 章）、CLAUDE.md / Skills / Hooks 三控制面（第 6 章）、str_replace 编辑与修复环（第 23 章）、子代理与 MCP 接入（第 8 章）。集成形态覆盖第 12 章的方式一（CLI/PTY）与方式二（Claude Agent SDK——Harness 库化的实例）。用它做"生产级 Harness 长什么样"的参照读物，比读任何框架文档都直观。

**GitHub Copilot（agent 形态）**：IDE 原生分发 + 与 PR/评审流程深度整合的路线。定位启示：**分发渠道本身是 Harness 之外的第七件**——同等机制质量下，住在工程师已有工作流里的产品采用阻力最小（第 22 章组织视角的印证）。

**Cursor**：IDE 整体形态（编辑器即产品），自建代码索引与检索栈——第 11 章"语义检索路线"在 Coding 场景的代表实现，与 grep 路线（第 11 章 2.5 节）构成现实中的两条技术路线对照。

**Devin（Cognition）类"自主软件工程师"**：云端工作区 + 浏览器 + 长时程任务的全自主叙事代表。工程教训恰是第 1 章的自主性光谱：演示的全自主与生产的 HITL 需求之间的落差，是这一类产品口碑波动的共同根源——评估时按第 13 章"自主性按风险配置"检验其审批与回滚设施，而非看演示视频。

**云端异步 Coding Agent（Codex 类 / 各家后台任务形态）**：任务进队列、云沙箱并行执行、以 PR 为交付物——第 23 章"并行 worktree 开发"的托管版：隔离（第 13 章）、门禁（第 18 章 GUARD/CI）、人守 merge 闸口，三件套一样不少，只是搬进了云。

## D.2 通用助手与计算机操作（成熟度：早期采用）

**Computer Use / Operator 类**（各家的浏览器与桌面操作 Agent）：以屏幕截图 + 点击键入为行动空间——OSWorld/WebArena（第 15 章）测的正是这类能力。现状判断用第 24 章三问：生产信号仍集中在表单填写、网页流程等窄场景；宽场景的成功率与延迟尚不支撑 SLA。它的结构性难点本书都讲过：验证信号稀薄（点完按钮"成没成"难判——对比第 23 章编译测试的富信号）、副作用难分级（页面上一个按钮可能是任何等级的操作，第 9 章分级失去静态判据）。

**Manus 类通用任务 Agent**：云端沙箱 + 浏览器 + 文件工作区的组合——第 9 章"文件系统即工作区"结论在非 Coding 场景的产品化印证；其"规划-执行分离 + 交付物落盘"的形态即第 4 章 P2E 与工作区模式的合体。

## D.3 深度研究类（Deep Research 形态）

各家 **Deep Research** 产品（多轮检索 → 交叉验证 → 长报告）：第 11 章 Agentic RAG（检索即工具、追加检索回路）+ 第 4 章显式规划 + 引用溯源的产品化集成，是"非 Coding 领域找到富验证信号"的一次成功示范——它的验证信号是**引用可回查**（每个结论锚到来源），部分替代了代码领域的测试。长时程（数分钟到数十分钟）运行依赖的正是第 12 章的生命周期管理与第 3 章的预算设施。

## D.4 低代码 / 工作流平台

**Dify、Coze（扣子）、n8n 及同类**：可视化编排 LLM 节点 + 工具节点的平台。用第 1 章 2.5 节的语言精确定位：**它们主要是 Workflow 产品，不是 Agent 产品**——控制流由画布上的连线（人）决定，模型在节点内填空。这不是贬义：路径可枚举的场景（客服 FAQ、审批流、内容管线）本就该用 Workflow（第 1 章的选型法则），这类平台是该形态的最低成本落地。边界也随之清晰：开放探索任务上它们的"Agent 节点"能力有限，且第三篇的生产件（评测/观测/成本归因）在平台内的深度参差——按第 12 章六大件逐件检查再定深度绑定。

## D.5 编排框架（代码库）

**LangGraph（LangChain 谱系）**：第 18 章显式图执行的最流行开源实现——state / conditional edges / checkpointer / interrupt 与本书图执行器的概念一一对应（读完第 18 章再看它的文档，会发现只剩 API 记忆工作）。LangChain 本体则是工具与集成的生态层，第 2 章的心智模型提醒依然适用：框架封装的是那 40 行循环，会手写才谈得上选型。

**CrewAI**：角色化多 Agent 的模板化封装（Supervisor / Pipeline 风格开箱即用）。用第 17 章语言评估它给的模板各是什么拓扑、代价系数多少；第 1 章坑 5（过早多 Agent）在这类"五分钟起多 Agent"的框架用户里发生率最高——Checklist（第 17 章）先行。

**AutoGen（Microsoft）**：对话式多 Agent（GroupChat 谱系）与事件驱动运行时。其"Agent 间自由对话"形态对应第 17 章 Debate/Swarm 的混合——token 放大与可预测性的账（第 17 章表）要先算。

**OpenAI Agents SDK / Swarm 谱系**：handoff 原语的命名来源（第 17 章 Swarm 拓扑）；轻量、贴近裸循环，适合验证概念。

**Claude Agent SDK**：Claude Code 的 Harness 以库形式开放——第 12 章"方式二：SDK 嵌入"的直接实例，也是"买六大件、自建定制层"路线的代表。

**框架选型的通用姿势**（本书立场重申）：先用第 2 章的手写循环建立心智模型 → 用第 12 章六大件清单逐件检查候选框架的实现与可替换性 → 缺的件按第三篇对应章节自建。**框架是六大件的采购清单，不是架构的替代品。**

## D.6 托管运行时与云服务

**云厂商 Managed Agents / Bedrock Agents / Vertex AI Agent Builder 及同类**：Harness 六大件的云服务化（第 24 章"运行时标准化"档位：早期采用）。与第 20 章部署光谱交叉评估：它们通常落在第二档（VPC/云边界内），买到的是运维与合规资质，让出的是 Harness 定制深度——"自建 K8s → 托管 K8s"的历史在 Agent 运行时上重演，迁移判断也同构：标准件托管、差异件自持。

## 使用纪律（三条）

1. **名单会过期，方法不过期**：本附录的任何产品描述以其当前文档为准；三坐标定位法（六大件 × 拓扑 × 集成/部署）是常青的。
2. **产品热度不进选型依据**：选型走第 20 章评分卡（合规硬门槛 → 自家评测集 → 五维打分），本附录只负责把候选放进正确的格子。
3. **读产品即读 Harness**：每个成熟产品都是一份活的 Harness 设计文档——用第 12 章图 1 对照着"拆"它，比读十篇测评收获大。这也是第 25 章三条延伸路径共同的日常练习。
